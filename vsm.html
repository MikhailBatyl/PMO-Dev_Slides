Дальнейшие действия

  1. 1
    ПриоритезацияPMO

    Разобрать 114 карточек в «Приоритезация / Готово» и 121 карточку старше 90 дней: взять в работу, отложить с датой или закрыть.

    В этой колонке одновременно не больше 20 карточек. За 2 недели старых (лежат 90+ дней) останется не больше 60.

  2. 2
    Ёмкость 1СPMO + Dev

    Не отдавать в разработку больше, чем команда успеет за спринт. Пока очередь длиннее спринта — новые карточки не добавлять.

    1С: 384 ч на продукт и 96 ч на баги. Очередь — не длиннее одного спринта (сейчас два).

  3. 3
    Разные правила для задачPMO

    Продукт, баг и срочное идут по разным правилам. Срочный баг не выкидывает продуктовую задачу без явного решения PMO.

    Среди закрытых задач баги — не больше четверти.

  4. 4
    Оценка: 1 SP = 4 часа1С

    Принимаем в работу по аналитике Kaiten: 1 story point = 4 часа (полдня одного разработчика). Спринт человека — 80 ч = 20 SP, шестеро 1С — 120 SP на спринт. Проставить оценку на 28 карточек 1С без размера.

    У каждой активной карточки 1С есть оценка. В «Готово» — дата закрытия, иначе очередь снова считают на глаз.

  5. 5
    Буфер спринта 80 / 20Оба

    80% спринта — запланированная ценность. 20% заранее оставляем на баги, срочное и замечания. Эту квоту нельзя заранее забить фичами.

    1С: 384 ч продукт + 96 ч буфер. Web: 512 ч продукт + 128 ч буфер.

  6. 6
    Обратная связьPMO + Dev

    После кода и на доске ценностей ответ заказчику — не дольше 3 дней. «Берём / не берём», замечание с приёмки и баг сразу возвращаются в портфель PMO, а не копятся до релиза.

    Карточка не висит неделями в «почти готово».

  7. 7
    Руководитель разработки и единый отчётPMO + Dev

    Добавить руководителя команды разработки. Операционные KPI — очередь, ёмкость, доля багов, срок обратной связи — вывести на одну информационную панель / отчёт, чтобы PMO и Dev смотрели одни цифры.

    Один отчёт на спринт вместо разрозненных выгрузок из Kaiten.

Как проектный отдел считает приоритет

Продукт

Новая ценность. PMO ставит ценность, разработка — размер. Смотрим клетку матрицы и отдаём сверху вниз, не больше ёмкости спринта.

Баг

Живёт в буфере 20% спринта. Считаем по критичности, в матрицу не кладём.

Срочное

Только явным решением PMO. Съедает буфер, не продуктовую очередь. Не ломаем работу в коде.

Клетка = приоритет

Ценность: слабый / средний / сильный. Размер: S до 2 SP · M 3–5 SP · L 8 SP и больше. Нет постановки — в матрицу не кладём.

Если размер одинаковый

  1. 1

    Есть SP — меньше SP выше. Две карточки M, 3 SP и 5 SP: сначала 3 SP.

  2. 2

    SP нет или тоже равны — кто раньше получил готовую постановку.

Где поток ломается и что менять — кайдзен PMO × разработка

Три типа ценности в одном потоке

Сейчас все типы идут по одной доске и конкурируют за одних разработчиков — без разных правил для задач.

Петли взаимодействия PMO и разработки

Сейчас: Push

PMO толкает задачи вниз. Вход 72 карт/спр при закрытии 44. 160 «готовы к разработке», 121 старше 90 дней. Разработка не «тянет» работу — она получает запас.

Слабая петля обратной связи

После релиза есть статус Receive feedback, но он не возвращает сигнал в приоритет PMO. Баги открываются сразу в Downstream и обходят портфель.

Цель: Pull

Разработка берёт следующую ценность, только когда есть свободная ёмкость. PMO держит очередь ≤ 1 спринта и решает «войти вместо замены».

Целевое состояние потока

Сейчас

  • Push: PMO наполняет запас
  • Сквозной LT 44,0 дн. (21,1 + 22,9), PCE 54%
  • Один поток на все типы работ
  • Очередь 1С = 2 спринта
  • Обратная связь не управляет входом

Цель (1–2 квартала)

  • Pull: Dev берёт по ёмкости
  • Lead time ↓, очередь PMO ≤ 1 спр.
  • Продукт / баг / срочное — разные WIP
  • Очередь 1С ≤ 1 спринта
  • Баг и ОС возвращаются в портфель PMO
Метод: Value Stream Mapping (бережливое производство) — текущее состояние + кайдзен. Не путать объём бэклога (сколько работы стоит) и ёмкость (сколько команда может взять за спринт). Ограничения: SP покрыты не полностью; время 1С и Web в разных единицах; массовые закрытия искажают отдельные дни.
