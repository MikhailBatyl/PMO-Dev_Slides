  3. 3
    Разные правила для задачPMO

    Продукт, баг и срочное идут по разным правилам. Срочный баг не выкидывает продуктовую задачу без явного решения PMO.

    Среди закрытых задач баги — не больше четверти.

  4. 4
    Оценка: 1 SP = 4 часаDev

    Принимаем в работу по аналитике Kaiten: 1 story point = 4 часа (полдня одного разработчика). Спринт человека — 80 ч = 20 SP, шестеро 1С — 120 SP на спринт. Проставить оценку на 28 карточек 1С без размера.

    У каждой активной карточки 1С есть оценка. В «Готово» — дата закрытия, иначе очередь снова считают на глаз.

  5. 5
    Буфер спринта 80 / 20Dev

    80% спринта — запланированная ценность. 20% заранее оставляем на баги, срочное и замечания. Эту квоту нельзя заранее забить фичами.

    1С: 384 ч продукт + 96 ч буфер. Web: 512 ч продукт + 128 ч буфер.

  6. 6
    Обратная связьPMO + Dev

    После кода и на доске ценностей ответ заказчику — не дольше 3 дней. «Берём / не берём», замечание с приёмки и баг сразу возвращаются в портфель PMO, а не копятся до релиза.

    Карточка не висит неделями в «почти готово».

  7. 7

    Добавить руководителя команды разработки. Операционные KPI — очередь, ёмкость, доля багов, срок обратной связи — вывести на одну информационную панель / отчёт, чтобы PMO и Dev смотрели одни цифры.

    Один отчёт на спринт вместо разрозненных выгрузок из Kaiten.

Как проектный отдел считает приоритет

Продукт

Новая ценность. PMO ставит ценность, разработка — размер. Смотрим клетку матрицы и отдаём сверху вниз, не больше ёмкости спринта.

Баг

Живёт в буфере 20% спринта. Считаем по критичности, в матрицу не кладём.

Срочное

Только явным решением PMO. Съедает буфер, не продуктовую очередь. Не ломаем работу в коде.

Приоритет = ценность ÷ размер (SP)

Чем больше пользы на единицу работы — тем раньше берём. Карточка попадает в клетку матрицы справа: строка — ценность, столбец — размер.
Ценность (ставит PMO): слабый = 1 · средний = 2 · сильный = 3. Размер (ставит Dev): точный SP; для клетки — S ≤ 2 · M 3–5 · L ≥ 8.
Пример: сильная S на 2 SP → 3 ÷ 2 = 1,5 — брать первыми. Слабая L на 8 SP → 1 ÷ 8 = 0,13 — не брать. Нет постановки — в бэклог не кладём.

Приток и склад багов на одной оси спринтов

Downstream 2.0 · спринты по 2 недели · 28.05–16.10.2026

В каждом спринте два столбика: слева приток, справа склад. Над стрелкой — часы переходящего склада на следующий спринт. Под стрелкой — сколько закрыли. Бирюзовая стрелка: закрыли ≥ завели; красная: закрыли меньше. Красные часы — выше буфера 224 ч.

1С Web Mobile бледный столбик — приток, плотный — склад
Формула склада
склад на конец = склад на начало + приток − закрыли

Пример спринта с 23.07 (на графике подписано у этой пары):

33 + 47 − 53 = 27

  • 33 — склад на конец прошлого спринта (с 09.07, плотный столбик)
  • 47 — приток с 23.07 (бледный столбик, из них Web 40)
  • 53 — закрыли за спринт (под стрелкой)
  • 27 — склад на конец с 23.07 (плотный столбик). Это не 47.
Что входит в расчётное время над складом
часы = (1С×3 + Web×2 + Mobile×2) SP × 4 ч

Оценка, сколько часов заберёт весь текущий склад, если закрывать его в следующем спринте.

  • Входит: открытые баги на конец спринта по платформам. 1С-баг ≈ 3 SP, Web/Mobile ≈ 2 SP (S). 1 SP = 4 ч, 1 чел. = 80 ч/спринт.
  • Не входит: новые баги следующего спринта, продуктовые задачи, PMO, факт списанных часов.

Пример 16.10: 4×3 + 5×2 + 16×2 = 54 SP × 4 ч = 216 ч ≈ 2,7 чел. Из них Mobile 16×2×4 = 128 ч при ёмкости Flutter 80 ч.

Серая подложка объединяет пару одного спринта. Не сравнивайте правый столбик спринта с левым столбиком следующего. Источники: выгрузки Kaiten 16.10.2026, Downstream 2.0.
